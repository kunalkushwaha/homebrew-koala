## Install, then run as you

<Tabs syncKey="host">
<TabItem label="macOS">

```sh
brew install kunalkushwaha/koala/koala
koala system install          # set up and start the manager for your user
```

You need a Mac with Apple silicon and macOS 26 or newer, and images built for
`linux/arm64`. To install from a release archive, see
[getting started](guide/getting-started/#installation).

</TabItem>
<TabItem label="Linux (preview)">

Download the `.deb` from the
[releases page](https://github.com/kunalkushwaha/homebrew-koala/releases) and
check its checksum against the release notes, then:

```sh
sudo apt install ./koala_VERSION_amd64.deb
koala system check            # what this host has, and what is missing
koala system install          # set up and start the manager for your user
```

You need Ubuntu 24.04 on x86-64 with kernel 6.12 or newer, access to
`/dev/kvm`, and images built for `linux/amd64`. See
[Koala on Linux](guide/linux/).

</TabItem>
</Tabs>

After the install, everyday use needs no `sudo`: the same `koala` commands
on both.

## From throwaway job to sandboxed agent

<Tabs syncKey="try">
<TabItem label="Throwaway job" icon="rocket">

A command in a fresh VM that is removed when the command ends:

```sh
koala run --image docker.io/library/alpine:3 -- /bin/sh -c 'echo hello from the guest; uname -m'
```

</TabItem>
<TabItem label="VM that stays up" icon="laptop">

Create a persistent VM and work in it:

```sh
koala create dev --image docker.io/library/alpine:3 --wait
koala start dev --wait
koala exec -it dev -- /bin/sh        # an interactive shell; type exit to leave
koala stop dev --wait
```

</TabItem>
<TabItem label="Sandboxed agent" icon="seti:lock">

An environment VM with the internet off and an API key that never enters
it. The key stays on your computer (in the login keychain on a Mac), and
the broker adds it to the requests the policy allows:

```sh
koala policy create openai-main --template openai --model gpt-4.1-mini   # asks for the key
koala create agent --image docker.io/library/alpine:3 --no-internet \
  --broker openai=openai-main --wait
koala start agent --wait
koala exec agent -- sh -c 'echo $OPENAI_BASE_URL $OPENAI_API_KEY'
```

Inside the VM, the service is `http://openai.broker.koala.internal/v1`, and
`OPENAI_API_KEY` is only a placeholder. See [keys outside the VM](guide/broker/),
[networking](guide/networking/) and the [Hermes example](guide/example-hermes/).

</TabItem>
<TabItem label="Agent from a template" icon="puzzle">

One command sets an agent up: its VM, the policy that keeps its key outside
the VM, a volume, and its setup. Koala shows the whole plan and asks first:

```sh
koala template list                     # the templates
koala create hermes --template hermes   # asks for the model key, shows the plan, then asks
```

See [VM templates for agents](guide/templates/), and the examples:
[Hermes](guide/example-hermes/), [OpenClaw](guide/example-openclaw/) (not
tested on Koala yet) and [an X agent](guide/example-x-agent/).

</TabItem>
</Tabs>

<p class="koala-eyebrow">04 · Tested by attacking it</p>

## Hostile guests, crashes and fuzzing, on real VMs

- **Root inside the VM attacks the boundary:** the guest channels, the
  network (spoofing, fragments, floods), storage and credentials, beside a
  healthy control VM, on lean and full VMs.
- **About 1,400 crash checks on each platform** kill the manager, each VM's
  process and every helper at chosen moments, then check that nothing is
  lost or left behind and the VM starts again.
- **Every parser of guest data is fuzzed:** more than 40 targets, each for
  at least 100,000 inputs, the Swift and C ones under AddressSanitizer.
- **A canary key is hunted** through the VM's disk, volumes and image; it
  may appear only on the upstream request.
- **Every release is checked as you get it:** a simulated fresh Mac, an
  upgrade from the previous release with a VM running, and a clean install
  on each platform.

More in the [README](https://github.com/kunalkushwaha/homebrew-koala#how-koala-is-tested).

<p class="koala-eyebrow">05 · Defaults</p>

## What a VM can reach

| Resource | Default | When you grant it |
| --- | --- | --- |
| Internet | Public addresses only | Can be switched off |
| Files on your computer | None | Folders you share; read-only unless you ask for read-write |
| Secrets | None | Named secrets, to one VM, as a file or an environment variable |
| API keys | None | A broker grant: the key stays on your computer, added only to the requests a policy allows |
| Services on your computer | None | One address and specific ports |
| Your LAN | None | A specific prefix and ports |
| Other VMs | Never | Not available in v0.1 |
| Published ports | None | On `127.0.0.1`, or on the LAN when you ask |

Koala treats everything inside a VM as untrusted, and trusts you, the
logged-in user. On a Mac, VMs stop when you log out; on Linux, they keep
running with lingering on. Nothing starts by itself after a restart.

<Aside type="caution" title="Koala is in preview">
Koala's security work is not complete, so use it with workloads and on
machines you trust. Each [release's notes](https://github.com/kunalkushwaha/homebrew-koala/releases)
say what is done and what is not. This site describes only what works today.
</Aside>
